## 2. 실호출 증빙 최소 세트 (27번용)

### 2a. 요청 구성: 채팅 **C 필수 + A 선택, 총 상한 2건**

코드 근거(1회차 검증 반영): `plan.py` `rule_tools("lookup")`은 `["get_financials"]`만 반환하고 `want_disclosures`는 screen·refine에서만 반영되며, `execute.py` lookup 분기는 `get_financials`만, `judge.py`의 `search_disclosures`는 screen·refine의 PASS 종목에서만 호출한다. 따라서 **공시(OpenDART)는 screen형 요청에서만** 나온다. lookup형에 공시를 요청하는 문구는 쓰지 않는다.

| 순번 | 질문(UI 입력) | 기대 Tool | 외부 호출(예상) |
|---|---|---|---|
| C 필수 (screen+공시) | `KOSPI 2차전지 중 ROE 5% 넘는 종목, 공시도 같이 보여줘` | `find_stock_candidates` 1(시세) + `get_financials` 6(재무·시세) + `search_disclosures`(PASS 종목당 1) | 공공데이터 ~25, OpenDART 2~4, GMS 2~3. 근거: 대표 요청 4 세션 `57e875c8`(조건 `2차전지 ROE>=5`)이 find 1 + get_financials 6 |
| A 선택 (lookup) | `삼성전자 ROE랑 PER 알려줘` | intent=lookup → `get_financials` 1(재무 `_fetch_fin` + 시세 `_fetch_price`) | 공공데이터 3~10, GMS 2~3, OpenDART 0 |

- C 한 건으로 시세·재무(공공데이터)·공시(OpenDART)·LLM(GMS)을 모두 밟는 것이 목표다. A는 "한 종목 조회형" 화면 증빙을 더할 때만 하며 생략 가능하다.
- **`want_disclosures` 규칙**: C에서 analyze가 `want_disclosures=true`로 추출했는지는 실행 후 `llm_decision`(tools 결정에 `search_disclosures` 포함 여부)과 `run_logs`의 `tool_call`로 확인한다. false(공시 호출 없음)이거나 PASS 종목이 0이면 **추가 호출 없이 공시·OpenDART 증빙을 '미확인'으로 두고** 8.7 보완 문서에도 그렇게 쓴다. 문구를 바꿔 재질문하지 않는다.
- 요청마다 **서버를 새로 기동**해(세션 메모리·도구 캐시 초기화) 캐시 적중 없이 실호출이 일어나게 한다. 같은 종목 재질문 금지.
- 채팅 요청 총 상한은 **2건**(C 1 + A 1). A는 C의 재시도로 쓰지 않는다. C가 실패하면 그것으로 끝(§5).

### 2b. 호출 상한(하드, 요청별)

| 요청 | 공공데이터 HTTP | OpenDART HTTP | GMS HTTP |
|---|---|---|---|
| C | **40** | **6** | **4** |
| A | **12** | **0** | **4** |
| 총량(C+A) | **52** | **6** | **8** (외부 HTTP 합 66 이하) |

- 요청별 상한은 서버를 요청마다 새로 띄우는 래퍼가 집행한다(래퍼 인자로 상한 전달). 총량은 요청별 상한의 합이다. 대표 요청 3(56초·수백 건)과 같은 요청은 쓰지 않는다.
- 상한 초과 시도는 해당 호출만 실패시키고(§2d) 즉시 중단·보고. 호출 전후 총량은 §2f 표로 남긴다.

1. 사전 점검(§4 사전 grep, DB 사본, 래퍼 기동)을 모두 마친다 — 외부 호출 0.
2. C 제출 → 완료 대기 → 캡처·네트워크 기록 확인 → `tool_result` 코드 확인(§2d).
3. A를 할 경우 **C 완료 후 최소 120초** 대기. C에서 연결 오류·중단 표식이 있었으면 A도 하지 않는다. A도 새 서버 프로세스로 한다.
4. 재계획이 일어나도 같은 요청의 호출 수에 포함되며 상한 내여야 한다. 새 요청은 이전 요청이 끝나기 전에 시작하지 않는다.

### 2d. 중단 규칙·차단 보호

- **첫 연결 수준 오류 즉시 중단·재시도 금지**: 래퍼가 `httpx.ConnectError`·`ConnectTimeout`·`RemoteProtocolError`·`ReadTimeout`(OpenDART·공공데이터 호스트) 또는 HTTP 429/403/5xx(**GMS 호스트 `gms.ssafy.io`의 429·5xx 포함**)를 **1건이라도** 보면 `STOP` 표식을 만들고 이후 모든 외부 호출을 실패시키며, 사람은 서버를 종료한다. `FIN_CONCURRENCY=5`라 `STOP` 이후에도 이미 시작된 호출이 최대 5건 더 나갈 수 있으므로 그 건수를 기록표에 적는다. 상한 초과 시 래퍼가 던지는 예외는 자체 정의 `class CapExceeded(httpx.TransportError)` 하나로 하여 Tool 래퍼가 `API_ERROR`로만 바꾸게 하고(서버 크래시 없음), 상한 초과는 계획된 차단이라 `STOP`을 걸지는 않지만 중단·보고 사유로 취급한다. 같은 날 재시도하지 않는다(메모리의 OpenDART IP 차단 이력). 화면에 `TIMEOUT`/`API_ERROR`가 보이면 재질문하지 않고 거기서 멈춘다.
- 중단 시: 확보된 캡처·기록만 쓰고 해당 칸은 `미확인`+사유(§5). 사용자에게 "외부 차단 징후"로 보고한다.
- 서버 stdout/stderr는 **반드시 스크래치 파일로 리다이렉트**한다(httpx INFO 로그가 serviceKey를 URL로 찍을 수 있음). 이 파일은 커밋하지 않고 §4 키 grep 대상에 넣는다. D1a 마스킹 필터가 래퍼 기동 경로(`uvicorn.run`으로 app 직접 호출)에서도 설치되는지 구현 시 확인한다.
- 기동 래퍼(스크래치패드 전용 스크립트, **저장소에 커밋하지 않음**, 코드 변경 아님): 현재 프로세스에서 `httpx.AsyncClient.send`를 감싸 호스트별 건수 카운트·상한·중단 표식을 처리하고 `uvicorn.run(backend.main:app, host=127.0.0.1, port=8765)`을 같은 프로세스에서 호출한다. **기록하는 것은 호스트명·건수·오류 클래스명뿐**이다(URL·쿼리·serviceKey·헤더 기록 금지, 25번과 충돌 방지).
- 8000번 포트는 사용자 서버이므로 접근·종료·요청 금지. 8765 점유 시 8766 사용(포트 변경은 기록).

### 2e. 실DB·사본 구분

1. 시작 전 `shasum -a 256 invest_helper.db`(실DB; 사용자 서버가 WAL로 쓰는 중이면 해시가 변할 수 있음 → **쓰기 시도 없음**을 증빙하는 것이 목적이므로, 사본 서버 cwd가 실DB와 다른 디렉터리임을 `lsof -p <pid>`/`pwd`로 확인하는 것을 대체 증빙으로 쓴다).
2. 사본 생성: `sqlite3 -readonly <repo>/invest_helper.db ".backup '<scratch>/copy/invest_helper.db'"`(WAL 포함 일관 사본). 저장소 `data/`·`.env`는 복사하지 않는다.

4. `tests/conftest.py`의 격리는 pytest 전용이라 이 서버와 무관하다.
5. 실행 후 사본 DB에 `run_logs`가 쌓인다. 실DB의 `run_logs` 행 수(1,909행, 40여 세션)가 사전·사후 동일함을 `sqlite3 -readonly`로 확인한다.

## 8. 위험·한계

- 기준은 사후 설정(측정 후)이다. 이를 숨기면 검증자가 순환 논리로 FAIL 처리할 수 있어 I31에 명시한다. 요청 3의 여유 3.89s는 외부 API 상태에 따라 재측정 시 60초를 넘을 수 있다는 한계를 남긴다(이번에 재측정하지 않음).
- 요청 4·5 session_id는 추정 일치일 뿐 원 기록이 아니다. 유일 특정이 안 되면 '미기록'.
- 8.7 키 발급 당일 기록은 만들 수 없다. 보완 문구는 대체가 아니다.
- 실호출은 OpenDART IP 차단 이력 때문에 최소화했다. C에서 LLM이 공시를 요청으로 추출하지 않으면 공시는 미확인으로 두며 추가 호출은 없다(총 채팅 상한 2건).
- 프런트엔드는 `/api/logs`를 호출하지 않으므로 네트워크 기록에서 그 경로는 직접 연 요청이다.
- 사용자 서버(8000)와 실DB는 건드리지 않는다. 사용자 서버가 WAL로 실DB를 갱신 중이면 사전·사후 행 수가 달라질 수 있어 "내가 쓴 흔적이 없음"은 포트·cwd·프로세스 확인으로 증명한다.
- 보고에 올릴 사용자 확인 사항: 27-(3) 통과 사유 수용 여부, 앱 작성자·점검자·점검 일시 칸(사용자 기입), manual-test-questions.txt 낡은 문구 정정 여부.

## 구현 시 확인 항목

- 요청 C의 실제 intent/Tool 선택(`llm_decision`)과 `want_disclosures` 추출 결과. 공시가 안 불렸으면 재질문 없이 공시·OpenDART는 미확인으로 남김.
- `.env`는 `backend/config.py`의 `load_dotenv()`가 호출 파일 위치에서 위로 탐색하므로 cwd가 달라도 로드될 가능성이 높다(코드 읽기, 실행 미확인). 키 값 출력 없이 오류코드(`MISSING_API_KEY` 여부)로만 확인.
- 래퍼 기동 경로에서 D1a 마스킹 필터가 설치되는지, 서버 로그 파일에 키 문자열이 없는지.
- 브라우저 pane `read_network_requests`가 파일로 저장 가능한 형태인지, CDP 대안(Chrome 설치 경로 `/Applications/Google Chrome.app`) 사용 가능 여부.
- 캡처 파일 저장 수단(D22 §1a와 동일 문제).
- `.env`가 서버 cwd가 달라도 로드되는지(`load_dotenv()` 탐색 방식), 로드 여부는 키 값 출력 없이 `/api/health`류 또는 응답 오류코드로만 확인.
- D1b throttle이 대표 요청 기록(2026-11-20) 실행 시점에 적용돼 있었는지(`git log`로 base.py의 `HOST_INTERVAL_S` 도입 커밋과 실행 시각 대조). 아니면 §1a의 "외부 API 호출 간격 포함" 서술을 "측정 당시 간격 적용 여부 미확인"으로 고친다.
- 요청 4·5의 DB 대조에서 세션 유일성(§1c), 요청 4 세션의 `NO_FINANCIALS` 1건 확인.
- 래퍼가 상한 초과 시 만든 실패가 `API_ERROR`로만 나타나는지(비정상 예외·서버 크래시 없음).
- 호출 기록 표(§2f)의 HTTP 건수는 래퍼 계수치만 쓰고, 계수가 누락되면 '미확인'으로 적는다(요청 3 기록처럼 추정치를 사실처럼 쓰지 않는다).
