# D2a 산업명 사전(`industry_terms.json`) 채우기 설계

상위: `docs/DESIGN.md`, `docs/design/D2-identity-industry.md` §5(A3, 산업 해석). 본 단위는 **데이터(JSON) 작성 + 테스트 보강**만이다. 코드(`resolve.py` 등) 변경 없음.

근거 수집: 구축된 `invest_helper.db`를 `mode=ro`로 조회(외부 API·.env 미사용). 4019개사 전부 `listed=1, detail_status='ok'`. `induty_code`는 2~5자리 혼재(2자리 44, 3자리 1406, 4자리 483, 5자리 2086). 4~5자리는 DART 값에서 끝자리 `0`이 잘린 형태가 섞인 것으로 보인다(예: DB하이텍 `2611`, SK하이닉스 `2612`) — **원인 미확인**, 접두 매칭이라 영향 없음.
**KSIC 분류명은 일반 지식이며 공식 표와 미대조("미확인")**. 접두는 아래 DB 기업 수·샘플로만 뒷받침되는 것을 넣는다.

## 1. 형식 (resolve.py 요구 그대로)

```json
[{"term": "반도체", "prefixes": ["261"]}, ...]
```
- 최상위는 배열, 항목은 `{term: str, prefixes: [str, ...]}` 두 키만. 동의어 필드·시장 구분 필드는 **코드가 읽지 않으므로 두지 않는다**.
- 동의어 = **같은 `prefixes`를 가진 별도 항목**. `resolve_industry`가 후보를 접두 집합으로 중복 제거하므로 동의어끼리 부분 문자열로 겹쳐도 `ambiguous`가 되지 않는다(예: "전지"가 2차전지/이차전지/배터리에 모두 포함돼도 `ok`).
- `prefixes` 원소는 `^\d{2,5}$` 문자열(`select_by_industry`가 검증). 시장(KOSPI/KOSDAQ) 구분은 D2 §1에 따라 D3가 주가 API로 처리 → 사전에 불필요.
- 로딩 검증: `_norm_term(term)`(NFKC·공백 제거·말미 `업종|산업|관련주|섹터|업` 1회 제거)이 길이<2이거나 중복이면 `ValueError`. 따라서 "건설"과 "건설업" 동시 등재 불가, **라틴 문자 용어 금지**(정규화가 소문자화하지 않아 "IT"는 입력 "it"와 불일치), 말미가 `업`인 용어는 피한다.
- 파일 인코딩 UTF-8(코드가 `encoding="utf-8"`로 읽음).

### 선택 이유 / 모호성
- **반도체 = 261**(2611 집적회로 + 2612 반도체소자 합집합, 95사). 2611·2612만 분리하면 "반도체"가 `ambiguous`로 갈 수 있어 합집합 접두 하나로 둔다. 반도체 **장비**(2927)는 별 항목, 접두가 겹치지 않는다.
- **삼성전자는 `반도체`에 안 잡힌다**: DB상 삼성전자 `264`(통신·방송장비 계열). 업종코드 기준 선별의 구조적 한계이며 사전에서 우회하지 않는다(종목명 질의는 `resolve_stock`). → §6-2.
- **은행 = 6412**(일반은행 17), 저축은행 6413 분리. 641로 묶으면 "은행" 요청에 저축은행이 섞이고 §4의 유사업종 단계가 무의미해진다.
- **KB금융·신한지주·우리금융지주는 `64992`**(기타 금융업 계열 93사: CJ·LG·삼양홀딩스 등 **비금융 지주회사 다수 혼재**)라 "은행"/"금융"에서 제외되고 `금융지주` 용어도 만들지 않는다(노이즈). 사용자 판단 필요 → §5 요청 R1. 단 "금융"(64·65·66)은 접두 `64`가 64992를 포함하므로 지주사·SPAC까지 들어오는 넓은 정의(n=505)이다.
- **자동차 = 30**(완성차 301은 5사뿐, 부품 303 110사 포함해야 의미 있음). 부품만은 `자동차부품`.
- **바이오 211 / 제약 212 / 제약바이오·의약품 21**: 바이오 기업 일부는 212에도 있으나 DB로 구분 불가 → 단순 분리, 넓게는 21.
- **화학 = 20**(2011 기초화학 + 204 기타화학 + 202 등). 정유(192)는 별도.
- **소프트웨어 = 582**: 62(컴퓨터 프로그래밍·시스템통합, 60사)와 63(정보서비스, 48사)은 용어 경계가 불분명해 이번 범위에서 제외(미확인). 게임은 5821(DB에서 크래프톤 확인).
- **유통 = 47(소매)**: 46(도매 180사)은 종합상사·무역이라 제외, 질의 노이즈 방지.
- 제외한 후보(DB 근거 약함 또는 경계 불분명): 디스플레이(2621/2622 구분 미확인), 엔터테인먼트(59: JYP는 5920이나 표본 작음), 가전, 금융지주, 방송(60), 화장품, 호텔/레저(551·561 각 3사).

### 용어 충돌·부분 문자열 점검 (실행 결과, 초안 JSON 기준)
- 정확 일치가 항상 우선: "통신"(61)과 "통신장비"(264), "자동차"와 "자동차부품", "식품"과 "음식료", "바이오"/"제약"/"제약바이오"는 모두 정확 일치로 `ok`.
- 의도된 `ambiguous`: "반도" → [반도체 95, 반도체장비 82], "전자" → [전자부품 192, 전기전자 788]. 되묻기로 이어짐(D2 §5-4 권고).
- 접미 처리: "은행업", "건설업", "유통업", "화학업종", "반도체산업", "반도체 관련주" → `ok`. "증권사", "게임주", "차", "IT" → `unknown`(요구 시 `증권사`·`게임주`는 동의어 항목으로 추가 가능; 같은 접두라 충돌 없음 — 선택 사항).
- 앞으로 항목 추가 시 주의: 접두 집합이 다른 용어가 기존 용어의 부분 문자열이 되면(예: "연료전지" vs "2차전지" 의 "전지") 짧은 질의("전지")가 `ambiguous`로 바뀐다. §4 테스트가 정확 일치만 검사하므로 이런 변화는 테스트에서 안 잡힌다 → 허용(의도 변경은 PR 리뷰에서 확인).

## 3. 대표 요청 2 "은행…"의 `similar_industries("은행")` (실측)
- 새 사전: `은행`→`["6412"]` → `similar_industries` = `["6413"]` (부모 `641` 아래 6413 저축은행 12사). 즉 유사업종 단계(D0 ②)가 저축은행을 확장 후보로 제시 → 의도에 부합.
- 사전이 `[]`(현재)일 때는 `resolve_industry` 자체가 `unknown`이라 `[]`.
- 참고(동일 방식 실측): 반도체 → `[262,264,263,265,266]`(전자 계열), 증권 → `[6619]`(SPAC 등 금융서비스 162사 — 노이즈), 보험 → `[652]`, 조선 → `[313,319]`, 게임 → `[5822]`, 바이오 → `[212,213]`, 철강 → `[242,243]`. 2자리 접두 용어(자동차 30, 건설 41/42, 통신 61, 식품 10 등)와 `2820`(부모 282 아래 타 4자리 없음)은 `[]`(코드가 L<3 확장 불가 / 형제 없음).
- **증권 → 6619 노이즈**는 D2 규칙상 수용(재계획 ②가 대안 후보를 추가하는 용도). 코드 변경 요청 아님.

## 4. 테스트 (코드 변경 없이 테스트 파일만 보강)
`tests/test_d16_ready.py`의 `real_terms` 픽스처를 재사용(실제 JSON 로드, DB 불필요):
1. **기존 `test_terms_file_format`**: 유지(로딩 검증).
2. **xfail 제거**: `test_representative_terms_present`에서 `@pytest.mark.xfail`를 삭제. 반도체·은행 `ok`는 정확 일치 경로라 DB 접근 없이 통과(실측: `반도체`→`['261']`, `은행`→`['6412']`).
3. **신규 `test_terms_schema`** (CI, DB 불필요): 모든 항목이 정확히 `{term,prefixes}` 키, `prefixes`는 비어 있지 않은 `^\d{2,5}$` 문자열 목록·항목 내 중복 없음; 대표 필수 용어 집합(반도체, 은행, 증권, 보험, 금융, 자동차, 바이오, 제약, 화학, 철강, 건설, 조선, 2차전지, 소프트웨어, 게임, 통신, 유통, 음식료, 전기전자)이 모두 존재.
4. **신규 `test_terms_exact_resolves_to_self`** (CI): 각 항목의 `term`을 `resolve_industry`에 넣으면 `status=="ok"`이고 `prefixes`가 해당 항목 접두와 같다(정확 일치 경로만 사용하므로 DB 불필요 — `ambiguous`가 나오면 `_n_listed`로 DB를 건드리므로 이 테스트가 실패해 곧 충돌 신호가 됨).
5. **실DB 점검(수동/선택)**: `INVEST_REAL_DB=1`일 때만 실행(`pytest.mark.skipif`, 기본 skip). 각 접두에 `resolve._n_listed(prefixes) >= 1`, 실패 시 용어·접두 출력. CI는 실DB 비의존. 픽스처 DB 기반 접두 검증은 불필요(접두-기업 매칭은 `test_d2`가 이미 검증).
6. **회귀**: 기존 337 passed 유지 목표. 단, 신규 테스트로 개수는 증가하고 xfail 2건이 pass로 이동. `README`의 "337 passed" 문구는 갱신 필요 여부를 구현 시 확인(README 수정은 본 설계 범위 밖, §6).

## 5. 상위/코드 변경 요청 (제안만, 임의 변경 안 함)
- **코드 변경 요청 없음.** 형식·검증·부분 일치 모두 현행 코드로 충족.
- R1(사용자 판단): `금융지주`/`은행` 확장에 `64992`를 포함할지. DB상 64992는 비금융 지주사 혼재(93사)라 이번 설계는 **제외**. 포함하려면 KB금융·신한지주만 구분할 방법(종목 지정 등)이 필요 → 별도 단위.
- R2(관찰): `_norm_term`이 소문자화하지 않아 라틴 용어("IT")는 사용 불가. 필요 시 `.lower()` 한 줄 추가를 제안(이번 범위 외).
- R3(관찰): `listed=1`에 상장폐지·구명칭 법인(하나IB증권, 한국씨티은행, 오렌지라이프 등)이 포함돼 n이 부풀려짐(D2 A6). 코드 변경 아님, 구축 데이터 한계.
- README §4의 "형식 예시일 뿐" 문구와 "빈 배열" 설명은 채운 뒤 사실과 달라지므로 문구 갱신을 별도 승인 하에 제안(test_readme_required_items는 `industry_terms.json`·`미확인` 키워드 유지 필요).

## 6. 구현 시 확인 항목
1. 상장폐지 법인 제외 여부(`corp_cls`/`stock_code` 기준) 실측 후 n 재확인 — 접두 선택에는 영향 없음 예상.
2. 삼성전자(264)가 "반도체" 질의에서 빠지는 점의 사용자 수용 여부(대표 요청 1에서 영향 확인).
3. KSIC 공식 표와 접두의 분류명 대조(특히 2927 장비 범위, 2820 전지 범위, 6619·649 계열).
4. 증권(6612)·제약(212) 등에서 `similar_industries` 확장 결과가 재계획에 적절한지 e2e에서 확인.
5. 초안 JSON 중 `전력가스`(35, 17사)·`항공`(6사)은 표본이 작음 — 유지/삭제는 구현자가 판단(삭제해도 테스트 필수 집합에는 없음).
6. 구현 범위: `backend/identity/data/industry_terms.json` 채우기, `tests/test_d16_ready.py`의 xfail 제거 및 신규 테스트 2~3개 추가. 그 외 파일 변경 없음.
